# AWS Serverless Cloud Infrastructure & Security Dashboard

A serverless AWS application for tracking cloud infrastructure resources and their security review status.

This project was built to develop hands-on experience with AWS cloud infrastructure, Infrastructure as Code (IaC), serverless application architecture, identity and access management, API security, and infrastructure deployment using Terraform.

The application provides a public dashboard for viewing infrastructure resources while restricting resource creation, modification, and deletion to authenticated administrators.

---

## Project Status

**Core Application Complete**

The application infrastructure is managed with Terraform and has been validated through a complete destroy and redeploy cycle. Cognito administrator users are intentionally managed separately from Terraform.

Deployment-specific configuration, including API Gateway, Amazon Cognito, and CloudFront values, is automatically generated by Terraform and provided to the frontend at deployment time.

## Architecture

The application uses a serverless AWS architecture consisting of:

- **Amazon CloudFront** — delivers the frontend over HTTPS
- **Amazon S3** — privately stores static frontend assets
- **CloudFront Origin Access Control (OAC)** — restricts direct access to the S3 frontend
- **Amazon Cognito** — provides administrator authentication
- **Amazon API Gateway** — exposes the application's HTTP API
- **API Gateway JWT Authorizer** — protects authenticated API operations
- **AWS Lambda** — processes API requests and application logic
- **Amazon DynamoDB** — stores infrastructure resource records
- **Amazon CloudWatch** — stores Lambda application logs
- **AWS IAM** — controls permissions between AWS services
- **Terraform** — provisions and manages the AWS infrastructure
- **HTML, CSS, and JavaScript** — provide the browser-based dashboard

### Request Flow

**Frontend delivery**

```text
Browser
   |
   v
CloudFront
   |
   v
Private S3 Bucket
```

**Authentication**

```text
Browser <----> Amazon Cognito
```

**Application API**

```text
Browser
   |
   v
API Gateway
   |
   v
Lambda
   |
   v
DynamoDB
```

**Application logging**

```text
Lambda
   |
   v
CloudWatch
```

Public read requests can access the API without authentication.

Write requests require a valid Cognito-issued JWT before API Gateway forwards the request to Lambda.

## Authentication and Authorization

The application separates public resource visibility from administrative resource management.

### Public Access

Unauthenticated users can:

- View all resources
- View individual resources
- View resource status
- View security review status

### Authenticated Access

Authenticated administrators can additionally:

- Create resources
- Edit existing resources
- Delete resources

Amazon Cognito provides administrator authentication using the OAuth 2.0 Authorization Code flow with PKCE.

Self-service account registration is disabled. Administrator accounts are created separately rather than being provisioned through Terraform.

After authentication, the frontend sends the Cognito access token in the HTTP `Authorization` header.

Protected API Gateway routes use a JWT authorizer to validate the token before allowing the request to reach Lambda.

This means authorization is enforced by the API infrastructure rather than relying only on frontend controls.

## API

The application exposes the following HTTP routes:

| Method | Route | Access | Purpose |
|---|---|---|---|
| `GET` | `/resources` | Public | Retrieve all resources |
| `GET` | `/resources/{id}` | Public | Retrieve a specific resource |
| `POST` | `/resources` | Authenticated | Create a resource |
| `PATCH` | `/resources/{id}` | Authenticated | Update a resource |
| `DELETE` | `/resources/{id}` | Authenticated | Delete a resource |

API Gateway routes requests to a Python Lambda function responsible for validation, application logic, and DynamoDB operations.

## DynamoDB Design

The application uses an Amazon DynamoDB table:

```text
serverless-security-dashboard-resources
```

The table uses:

```text
Partition Key: id
Billing Mode: PAY_PER_REQUEST
```

Global Secondary Indexes are defined for potential alternative access patterns:

```text
EnvironmentIndex
OwnerIndex
SecurityReviewIndex
```

These indexes support future query patterns such as retrieving resources by environment, owner, or security review status.

The current application retrieves the resource inventory using a DynamoDB scan, while individual resources are retrieved using their unique resource ID.

## Deployment Configuration

The frontend does not contain hardcoded AWS-generated deployment identifiers.

Terraform dynamically generates a `config.js` file containing values such as:

```javascript
window.APP_CONFIG = {
    apiBaseUrl: "...",
    cognitoClientId: "...",
    cognitoDomain: "...",
    redirectUri: "..."
};
```

The application loads this configuration before the main frontend JavaScript:

```html
<script src="config.js"></script>
<script src="app.js"></script>
```

The frontend can then access deployment-specific values through:

```javascript
window.APP_CONFIG
```

This allows resources such as API Gateway, Cognito, and CloudFront to receive new AWS-generated identifiers during a deployment without requiring those values to be manually inserted into the frontend source code.

## Security Controls

Security was incorporated into both the application and infrastructure design.

### Frontend Hosting

The frontend S3 bucket:

- Blocks public access
- Uses S3 Object Ownership controls
- Uses server-side encryption with AES-256
- Has versioning enabled
- Is accessible to CloudFront through Origin Access Control

Users access the application through CloudFront rather than directly through the S3 bucket.

### HTTPS

CloudFront redirects HTTP requests to HTTPS.

### Security Headers

The CloudFront distribution uses an AWS-managed security headers policy to provide additional browser security protections.

### Authentication

Amazon Cognito provides administrator authentication.

Self-service user registration is disabled so application users cannot create their own administrative accounts.

### API Authorization

API Gateway uses a Cognito-backed JWT authorizer for:

```text
POST
PATCH
DELETE
```

Read operations remain publicly accessible.

### OAuth 2.0 + PKCE

The browser application uses the OAuth 2.0 Authorization Code flow with Proof Key for Code Exchange (PKCE), avoiding the need to store a Cognito client secret in frontend code.

### Least-Privilege IAM

The Lambda function is granted only the DynamoDB operations required by the current application:

```text
PutItem
GetItem
UpdateItem
DeleteItem
Scan
```

The Lambda function does not currently receive unnecessary DynamoDB query or index permissions.

### API Throttling

API Gateway applies default request throttling:

```text
Rate limit: 10 requests/second
Burst limit: 20 requests
```

This provides basic protection against excessive request volume.

### CORS

API Gateway restricts allowed origins and explicitly permits the headers and methods required by the application.

Authenticated requests use the `Authorization` header.

### CloudWatch Log Retention

Lambda application logs are stored in CloudWatch with a 14-day retention period rather than being retained indefinitely.

### Safer DOM Rendering

Resource data displayed by the frontend is rendered using DOM APIs such as `textContent` instead of directly inserting untrusted resource values as HTML.

### Sensitive Files

Terraform state, local Terraform directories, credentials, and other generated or sensitive files are excluded from version control through `.gitignore`.

## Deployment and Reproducibility

A major project milestone was validating that the application could be rebuilt from Terraform rather than depending on manually created AWS infrastructure.

The infrastructure was completely destroyed using Terraform:

```bash
terraform plan -destroy
terraform destroy
```

Terraform removed **31 AWS resources**.

The project was then rebuilt using:

```bash
terraform plan
terraform apply
```

Terraform created **32 AWS resources** from the configuration.

The rebuilt environment received new AWS-generated identifiers for resources including:

- API Gateway
- Cognito user pool
- Cognito application client
- CloudFront distribution

Terraform automatically propagated the new deployment values to the frontend through the generated `config.js`.

After redeployment:

- Cognito administrator access was re-established
- Public resource retrieval was validated
- Authentication was validated
- Resource creation was validated
- Resource editing was validated
- Resource deletion was validated
- Sign-out behavior was validated

A subsequent Terraform plan returned:

```text
No changes. Your infrastructure matches the configuration.
```

This confirmed that the deployed infrastructure matched the Terraform configuration after the full rebuild.

## Key Engineering Decisions

### Private S3 Instead of Public Website Hosting

The frontend bucket is not publicly accessible.

CloudFront accesses S3 using Origin Access Control, allowing the application to be publicly available without exposing the underlying S3 bucket.

### Public Reads, Authenticated Writes

Infrastructure information can be viewed without authentication, while modifications require administrator authentication.

Authorization is enforced at API Gateway rather than relying solely on whether the frontend displays administrative controls.

### OAuth Authorization Code Flow with PKCE

Because the application is browser-based and cannot safely store a client secret, Cognito authentication uses Authorization Code + PKCE.

### Least-Privilege Lambda Access

Lambda receives only the DynamoDB permissions currently required by the application.

Unused `Query` and DynamoDB index permissions were removed after reviewing the application's actual access patterns.

### Terraform-Generated Frontend Configuration

AWS-generated resource identifiers are not hardcoded into the frontend.

Terraform generates the deployment configuration from the infrastructure it creates, improving reproducibility.

### Terraform-Managed Logging

The Lambda CloudWatch log group is explicitly managed by Terraform so retention settings and lifecycle behavior remain part of the infrastructure configuration.

### Serverless Architecture

API Gateway, Lambda, DynamoDB, S3, CloudFront, and Cognito were selected to build the application without requiring persistent application servers.

This keeps infrastructure management focused on AWS service configuration, permissions, application integration, and Infrastructure as Code.
